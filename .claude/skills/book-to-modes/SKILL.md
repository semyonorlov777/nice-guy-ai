# Book-to-Modes: Проектирование режимов онлайн-тренажёр по книге

## Обзор

Этот скилл превращает книгу по психологии/саморазвитию в набор из 6-8 режимов онлайн-тренажёра с готовыми системными промптами для Gemini API.

**Вход:** Название книги (+ опционально PDF/текст книги). Если у автора несколько связанных книг — можно объединить.
**Выход:** MD-файл с детализацией режимов + MD-файл с готовыми промптами + landing_data JSON + таблица технического маппинга

## 🔴 Перед началом (блокирующий шаг)

**Порядок обязательный — без runbook читать остальное бесполезно, потому что все правила формата кросс-ссылаются туда:**

Скилл лишь оркестрирует пайплайн; правила живут в runbook. Без этого шага гарантированы рецидивы (после прошлых 6 книг каждый раз приходилось делать ~6 fix-*.sql на эти же правила).
1. Прочитай `references/REFERENCE.md` — 53 принципа, 5 архетипов, промпт-шаблон, типология replies, антипаттерны, принципы лендинга (Л1-Л7).
2. Прочитай `references/PLATFORM_MAP.md` — как режимы ложатся на код платформы (таблицы БД, chat_type, SQL, landing_data JSON-схема, **линтер `npm run check:chats`**).
3. Просмотри `examples/` — конспекты решений по прошлым книгам (что сработало, что нет).
3.5. **Прочитай эталонный seed-файл** одной из свежих книг (`scripts/seed-heroes-and-outlaws.sql` или `scripts/seed-pishi-sokraschay.sql`) — это живой пример полного набора полей и их структуры. Не копируй из него — копируй понимание: какие колонки заполнены, как структурирован landing_data, какие ключи `main_concepts`, `hub_messages`, `features`. Так быстрее научишься чем по схеме, и не пропустишь поле, которое в шаблоне ниже не выделено.
4. Если пользователь приложил PDF/текст книги — прочитай его.
5. Если книга не приложена — используй свои знания. Для малоизвестных книг предупреди, что нужен текст.

## Чеклист: объединение книг

Перед началом работы проверь — нужно ли объединять несколько книг в одну программу.

**Когда объединять:**
- У автора 2+ книги, которые дополняют друг друга (теория + практика, диагностика + лечение)
- Одна книга без другой «неполна» — читатель застревает на полпути
- Книги образуют естественную прогрессию

**Примеры:**
- Берн: «Игры» (1964) + «Люди, которые играют в игры» (1972) → объединены в одну программу
- Готтман: «7 принципов» + «The Relationship Cure» → можно объединить
- Одиночная книга → не объединять

**Как объединять:**
1. Определи части программы как прогрессию: «Увидеть → Понять → Действовать» (или другую)
2. Распредели режимы по частям
3. Маппинг: какая книга даёт материал для какой части
4. В таблице режимов добавь колонку «Часть программы»

**Когда НЕ объединять:**
- Книги на одну тему, но разных авторов (Гловер + Берн — это разные программы)
- Книга самодостаточна (Гловер «Славные парни» — одна книга = одна программа)

## Процесс (5 этапов с паузами)

**Ретроспективная модальность.** Если книга уже существует на платформе (есть программа, лендинг и режимы), но теста нет и задача — добавить тест — это отдельный путь: сразу переходи к **Этапу 4.1-retroactive «Ретроспективное добавление теста»** (ниже). Этапы 1-3 пропускаются: архетипы, режимы и промпты уже зафиксированы в БД. Прецеденты: `razgovorny-gipnoz` → `hypnosis-test`, `100-notes` → `100-notes-test`.

### Этап 1: Анализ книги

Изложи:

**Ключевые концепции** — 3-5 главных идей книги. Не пересказ, а «что читатель должен усвоить».

**Навыки/трансформации** — что книга обещает. Формулируй как навык: «распознать X → перестроить Y → получить Z».

**ЦА** — пол, возраст, контекст, уровень боли (низкий = «хочу лучше», средний = «есть проблема», высокий = «кризис»).

**Боли** — 4-6 штук от первого лица: «Я стараюсь, а он/она...», «Не могу понять почему...». Это будущие welcome replies.

**Категория книги** (`programs.category`) — `psychology` или `marketing` (text, не enum — добавлять новые жанры дёшево). По умолчанию `psychology`. Marketing — книги про коммуникацию, бренд, копирайтинг, влияние (`pishi-sokraschay`, `heroes-and-outlaws`, `borba-za-vnimanie`). Решение зафиксируй явно — попадает в INSERT INTO programs.

**Если объединяешь книги** — укажи какие концепции из какой книги, и как они складываются в прогрессию.

### Этап 1.5: Terminology canon checkpoint (если применимо)

**🔴 Это стоппер.** Для книг с насыщенной профильной терминологией AI не идёт к Этапу 2 (архетипы) пока не получит единый русскоязычный канон через два независимых Deep Research. Это правило появилось после программы `transdiagnostic-cbt` (Frank & Davidson 2014) — её пришлось задним числом русифицировать массовыми правками по полям БД, потому что режимы / тест / welcome / лендинг были засеяны с переизбытком английских терминов. Канон должен фиксироваться ДО проектирования, а не после.

#### Когда применять (5 критериев, нужно ≥3)

| # | Критерий | Проверь для своей книги |
|---|----------|-------------------------|
| 1 | Книга — clinical / medical / academic / legal / специализированная профессиональная (не self-help / motivation / общая публика) | … |
| 2 | ЦА — practicing professionals / advanced students / certified specialists (не «все, кто интересуется темой») | … |
| 3 | Английская книга без официального русского перевода ИЛИ книга с собственной авторской терминологией, не пересекающейся со стандартами поля | … |
| 4 | ≥10 специальных терминов из профильной области, у которых неочевиден русский эквивалент (или есть несколько конкурирующих переводов) | … |
| 5 | Перевод базовых терминов может иметь клинические/смысловые последствия (бытовой шлейф, искажение значения) | … |

**Уровни срабатывания:**

| Критериев | Решение |
|---|---|
| 0-2 | **Пропускаем.** Standard process: сразу к Этапу 2. Для саморазвития, мотивации, бытовых тем (Гловер, Кехо, Чепмен, Радикальное прощение) канон не нужен — русские эквиваленты устоявшиеся и однозначные. |
| 3-4 | **Рекомендуется DR**, но AI может пройти без него с явным риск-warning'ом пользователю: «Книга на грани критериев. Если решим пропустить — заложи в Этап 5 (ретроспектива) проверку терминологической согласованности после деплоя; вероятно потребуются точечные правки». |
| 5/5 | **ОБЯЗАТЕЛЬНО (hard stop).** Без unified canon document не переходим к Этапу 2. |

#### Обоснование

Прецедент `transdiagnostic-cbt` (May 2026, ретроспектива в `examples/transdiagnostic-cbt.md`):

- Книга — clinical CBT для practicing psychologists. Английский оригинал, нет русского перевода. Десятки терминов где русский эквивалент важен (`case formulation`, `safety behaviour`, `cognitive distortions`, `automatic thoughts`, `experiential avoidance`, …) и где машинный перевод даёт клинические ошибки (`safety behaviour` → «безопасное поведение» = бытовая ассоциация с ОБЖ; правильно — «охранительное поведение»).
- Программа была создана с переизбытком английских терминов в чатах, welcome, тесте и лендинге.
- После деплоя пришлось делать **отдельную задачу русификации** — синтез двух независимых Deep Research (Claude + Gemini), unified canon document, массовая правка по полям БД через `jsonb_set`.

Если бы canon собрался на Этапе 1.5 — все режимы / тест / лендинг сразу строились бы на правильной терминологии. Сэкономили бы ~3-5 часов и избежали ретеста UI на десятках поверхностей.

#### Процесс

1. **AI делает анализ книги** (Этап 1: концепции, ЦА, боли, навыки).
2. **AI проверяет 5 критериев** — заполни таблицу выше, посчитай сколько «да».
3. **Если ≥3 критериев — стоп.** Не переходи к Этапу 2. Сформулируй **два DR-промпта** (Gemini Deep Research + Claude Research) по шаблону из [`references/terminology-canon-prompt-template.md`](references/terminology-canon-prompt-template.md). Подставь плейсхолдеры: название книги, авторы, год, ISBN, ЦА, область, ~30-50 терминов, конкретные русскоязычные источники.
4. **Запусти оба DR параллельно** (не один за другим — независимо, чтобы не контаминировать через свою редактуру). Заказчик запускает по платной подписке Gemini + claude.ai/Research, возвращает результаты.
5. **AI синтезирует unified canon document** по образцу [`docs/books/transdiagnostic-cbt-terminology-canon-unified.md`](../../../docs/books/transdiagnostic-cbt-terminology-canon-unified.md). Сохраняет:
   - `docs/books/{slug}-terminology-canon-claude.md` — резюме Claude Research
   - `docs/books/{slug}-terminology-canon-gemini.md` — резюме Gemini Research
   - `docs/books/{slug}-terminology-canon-unified.md` — финальный синтезированный канон
6. **Покажи unified пользователю.** Только после подтверждения — переход к Этапу 2 с уже зафиксированной терминологией.

#### Что входит в canon (структура unified document)

- **Таблицы замен по категориям:** структурные термины, когнитивные конструкты, поведенческие конструкты, эмоциональные конструкты, методики/подходы, опросники/шкалы, специальные концепции
- **Метаправило для правки** — где русский, где гибрид, где английский по типу поля БД (system_prompt vs welcome vs replies vs landing vs test_configs)
- **Правило первого упоминания** — для HYBRID-терминов: «русское название (English term)» при первом появлении, далее только русское
- **Запрещённые переводы** — таблица клинических/смысловых ошибок с обоснованием
- **5+ методологических принципов** — общие правила, по которым строился канон
- **Применение к полям БД** — пронумерованный список с приоритетами
- **Контекстные исключения** — где канон не применяется (имена клиентов из книги, цитаты, библиография, технические ключи)
- **Что НЕ менять** — имена авторов, технические slug'и, JSON-структуры
- **Ссылки на исходники** — пути к двум resumé двух DR

Полный шаблон формата — `docs/books/transdiagnostic-cbt-terminology-canon-unified.md`.

#### Импликации на следующие этапы

Канон применяется ко **всему** видимому пользователю контенту:

| Этап | Где применяется канон |
|---|---|
| Этап 2 (архетипы) | Названия режимов в таблице, краткие описания |
| Этап 3 (детализация) | `welcome_title`, `welcome_subtitle`, `welcome_ai_message`, `welcome_replies`, формулировки в фазах диалога |
| Этап 4 (system prompts) | `programs.system_prompt`, `programs.author_chat_system_prompt`, `programs.anonymous_system_prompt`, каждый `program_modes.system_prompt` |
| Этап 4.1 (тест) | `test_configs.questions[].text`, `scales[].name`, `radar_label`, `interpretation_prompt`, `ui_config.welcome_title/description` |
| Этап 4.5 (лендинг) | Все секции `programs.landing_data`, `programs.hub_messages`, `programs.free_chat_welcome`, `programs.author_chat_welcome` |

**Без canon** → потом массовая правка БД через `jsonb_set` + ретест UI на десятках поверхностей. Это лишняя работа, и часть мест неизбежно будет пропущена.

**⏸ СТОП. Если стоппер активирован (≥3 критериев) — дождись подтверждения unified canon перед переходом к Этапу 2.**

### Этап 2: Маппинг на архетипы

Определи **тип книги** и примени паттерн размножения (см. REFERENCE.md секция 1).

Формула: 5 базовых архетипов + 1-2 подвида самого релевантного = **6-8 режимов** + обязательный **Свободный чат**.

Предложи таблицу:

| # | Название | Архетип | Блум | Часть программы | Суть (1 предложение) |
|---|----------|---------|------|-----------------|----------------------|

Колонка «Часть программы» — обязательна для объединённых книг, опциональна для одиночных.

Объясни: почему именно так, что НЕ включил и почему.

**Checkpoint: нужен ли тест?**

Заполни таблицу критериев (REFERENCE.md §12, нужно ≥3 из 5):

| # | Критерий | Для твоей книги | ✅/⚠️/❌ |
|---|----------|-----------------|---------|
| 1 | Диагностическая/навыковая модель ≥3 шкал | ... | |
| 2 | Шкалы ортогональны (измеряют разное) | ... | |
| 3 | Результат персонализирует дальнейший путь | ... | |
| 4 | Ликерт-утверждения применимы (не эссе) | ... | |
| 5 | Тест работает как воронка (shareable) | ... | |

Отдельно — **достоверность источников** (REFERENCE.md §12 «Книги без полного текста»):
- Полный текст книги есть? / Только фрагменты (рецензии, лекции, соцсети)?
- Если фрагменты — есть ≥20 HIGH-уверенных авторских цитат? Распределены ли они по ≥3 на кластер?
- Если <20 или какой-то кластер <3 → отмечай как ⚠️ и планируй Deep Research ДО SQL-дизайна (см. §12 «Правила атрибуции»).

**Явный вывод:** GO / NO-GO с обоснованием.
- Если GO — укажи: «Тест: да, ~N вопросов, K шкал» + названия шкал и их связь с режимами
- Если NO-GO — укажи «Тест: нет» и почему (какого критерия не хватает, или недостаточно авторского материала; предложи альтернативы из §12)

Покажи checkpoint пользователю. Только после подтверждения переходи к дизайну шкал.

**⏸ СТОП. Дождись подтверждения пользователя.**

### Этап 2.5: Анкета пользователя (опционально)

Анкета — короткий 3-вопросный опрос пользователя при первом заходе в программу. Ответы хранятся user-level (таблица `user_profile_responses`), инжектятся в каждый чат-промпт как блок «КТО ПЕРЕД ТОБОЙ» и используются для фильтрации тем хаба + welcome-сценариев.

**Прецедент:** пилот на книге Гловера (май 2026). Архитектура и инфраструктура подробно описаны в [PLATFORM_MAP.md → «Анкета пользователя»](references/PLATFORM_MAP.md). Этот этап — про **проектирование вопросов** для конкретной книги.

#### Когда применять (определитель — 4 критерия)

Если ≥3 «да» → анкету **стоит** делать. Иначе пропусти этот этап.

| # | Критерий | Объяснение |
|---|----------|------------|
| 1 | Книга про **личную трансформацию** (отношения, психология, навык общения) | НЕ marketing/копирайтинг где запрос объективен |
| 2 | У ЦА есть **конкретная боль/запрос**, который книга решает | Не «общее саморазвитие», а «не могу сказать нет жене» / «не понимаю эмоций партнёра» |
| 3 | Темы программы (`program_themes`) **разнообразны** (≥4 темы) | Иначе фильтровать нечего — все темы пойдут |
| 4 | Welcome без персонализации звучит **слишком обобщённо** | Если приветствие «о чём поговорим?» одинаково для всех — анкета его улучшит |

**Пропускаем для:** marketing-книг (`pishi-sokraschay`, `borba-za-vnimanie`, `heroes-and-outlaws`), книг с одной центральной темой (Кехо «Подсознание»), книг где уже есть калибровочный чат-режим (Ильяхов).

**Делаем для:** книг про отношения / границы / эмоции / семейные паттерны, где у пользователя есть **запрос от первого лица** и темы программы покрывают разные грани этого запроса.

#### Что проектировать (3 вопроса по SPIN-структуре)

3 вопроса — это пилотный стандарт. Минимум-достаточный для AI-фильтра тем и инжекции в промпт.

| `question_id` | Что выясняем | Тип | Формулировка под книгу |
|---|---|---|---|
| `context_intent` | **Что привело** — кратко, на чипах для скорости | `hybrid` (4 чипа + textarea) | «Что привело тебя к этой книге?» с 4 типовыми ответами + поле для своего |
| `problem` | **Что не так** — боль | `open_text` | «Что в твоих [отношениях/работе/...] сейчас идёт не так?» |
| `need_payoff` | **Точка Б** — как поймёт что сработало | `open_text` | «Как ты поймёшь, что эта программа сработала?» |

**Антипаттерны:**
- ❌ Больше 3-х вопросов — пользователь скипает.
- ❌ Слишком абстрактные формулировки («каковы ваши ценности?»). Под книгу всё конкретно: для Гловера — про угождение и границы, для Берна — про игры и роли, etc.
- ❌ Вопросы с прямой подсказкой на «правильный» ответ.
- ❌ Использовать `implication` (4-й SPIN-вопрос) — не работает на холодном пользователе. Если очень нужно — оставь только для soft-onboarding-вытаскивания из чата (см. `lib/personalization.ts`).

**Шаблон чипов для `context_intent` (типовые причины):**
- 4 варианта (не 3, не 5) — больше не помещаются в мобильный UI.
- `value` — короткий ключ (`pleasing`, `needs`, `authenticity`, `boundaries`).

| `welcome_replies` | Кнопки-подсказки | JSONB **объекты** `[{text, type}]`. Не строки. Последний `type: "exit"`. Каждый text ≤60 символов, без вложенных «ёлочек». |

**Контентный шаблон для `welcome_ai_message`** (рендерится в этом поле — без эмодзи+title в начале):


**Контентный шаблон для `welcome_replies` (3-4 reply, последний — exit):**

```json
[

  {"text": "[Другая ситуация]", "type": "normal"},
  {"text": "[Третья ситуация]", "type": "normal"},
  {"text": "Мне сложно сформулировать", "type": "exit"}
]
```

**⚠️ welcome_ai_message рендерится PLAIN TEXT** (без ReactMarkdown — см. [NewChatScreen.tsx:185](../../../components/chat/NewChatScreen.tsx:185) + [chat-message-formatting runbook](../../../docs/runbooks/chat-message-formatting.md)):

- Между абзацами — ТОЛЬКО `\n\n` (двойной перенос). Без него абзацы склеятся в стену — `.nc-ai-text` имеет `white-space: pre-line`, но одиночный `\n` = одна строка.
- Буллет — символ `•`, не markdown `-`/`*` (они напечатаются буквально).
- Не используй `**bold**`, `#` заголовки, нумерованные списки — все эти символы появятся в тексте как литералы.
- Не начинай с `эмодзи + Название режима` — заголовок уже рендерится отдельной карточкой над сообщением (wc-title).

Прецедент: eq-2-0 welcome у всех 5 режимов первоначально рендерился слипшейся стеной — пока не добавили `white-space: pre-line` (коммит `0075501`). Но даже с фиксом без `\n\n` между абзацами сообщение читается как monolith.

**⚠️ Антипаттерны в тексте reply** (проверь каждый reply перед записью в SQL):

- ❌ **Вложенные «ёлочки» внутри reply:** `«Что значит «развитие»?»` — parseQuickReplies regex non-greedy, захватит только до первого `»` → кнопка будет с обрезанным текстом. Убирай внутренние кавычки или переформулируй.
- ❌ **Пунктуация снаружи «ёлочек»:** `«Текст».` — точка вне кавычек ломает regex `[»]$`. Вся пунктуация — только внутри.
- ❌ **Markdown внутри reply:** `«Это **важно**»` — звёздочки видны буквально в UI.
- ❌ **Reply длиннее ~60 символов** — не влезает в кнопку на мобилке.

### Технические детали runtime (FYI для автора seed)

Что код делает поверх seed — знай, чтобы не дублировать работу и не путаться:

1. **QR-reminder auto-inject.** [app/api/chat/route.ts](../../../app/api/chat/route.ts) добавляет напоминание про «ёлочки» в **КОНЕЦ** system_prompt перед отправкой в Gemini (recency effect — последнее видит модель). Это страховка от мелких сбоев модели. **НЕ повод опускать блок `### Quick replies — ФОРМАТ` в seed:** reminder применяется только в `/api/chat`, не в `/api/chat/anonymous` (где есть свой укороченный) и не в `/api/test` (где идёт `programs.test_system_prompt`). Промпт в seed должен быть самодостаточным.

2. **Welcome serialization for F5.** В seed мы пишем `welcome_ai_message` и `welcome_replies` в **разные поля** БД. Runtime-функция `serializeWelcomeWithReplies` в [lib/chat/prepare-context.ts](../../../lib/chat/prepare-context.ts) склеивает их в один text с «ёлочками» в конце и сохраняет в `messages.content` — чтобы после F5 (или загрузки истории) `parseQuickReplies` восстановил кнопки из сохранённого текста.
   - **НЕ заполняй `welcome_message` (legacy) и `welcome_ai_message` одновременно** — приоритет идёт legacy → новые поля теряются. Линтер `npm run check:chats` это ловит (`welcome-message-exclusive`).

3. **AIBubble + QuickReplyBar split.** Все чат-поверхности (ChatWindow, NewChatScreen, AnonymousChat) рендерят ИИ-сообщения через ДВА компонента из [components/chat/ChatMessage.tsx](../../../components/chat/ChatMessage.tsx). `QuickReplyBar` — SIBLING контейнера `.msg`/`.nc-msg`, **НЕ внутри**. Эта деталь не должна волновать автора seed, но влияет на новые чат-экраны: если делаешь — следуй шаблону из runbook §"Шаблон для нового чат-экрана". Прецедент: первая итерация (2026-04-23) рендерила кнопки внутри flex-row — они уехали в узкую колонку справа.

4. **Иерархия system_prompt при выборе.** `lib/chat/prepare-context.ts::loadProgramContext` (строки 146+) выбирает по приоритету:
   1. `program_modes.system_prompt` (для tool-режимов — переопределяет программный, **правила не наследуются**)
   2. `programs.author_chat_system_prompt` (если `chatType === "author"`)
   3. `programs.system_prompt` (дефолт для free_chat и всех тем — `program_themes.welcome_system_context` подмешивается именно к нему через префикс `КОНТЕКСТ ТЕМЫ:`)

   **Импликация:** блок `### Quick replies — ФОРМАТ` обязан быть в КАЖДОМ из этих 3 полей. Если только в одном — другие пути генерации идут без правил.

### Этап 4.1: Создание теста (если решили «да» на этапе 2)

Если на этапе 2 решили, что тесту быть — создай полный seed SQL-файл. Принципы дизайна вопросов — REFERENCE.md секция 12. Полный SQL-шаблон, схема всех JSONB-полей и чеклист — PLATFORM_MAP.md секция «test_configs».

#### Что делать

1. **Спроектировать контент** — шкалы, вопросы, интерпретации (см. ниже)
2. **Заполнить SQL-шаблон** из PLATFORM_MAP.md → «SQL-шаблон создания теста»
3. **Проверить по чеклисту** из PLATFORM_MAP.md → «После создания теста — чеклист»
4. **Сохранить** как `scripts/seed-{book-slug}-test.sql`

⚠️ **Критичные моменты (из lessons learned):**
- `programs.test_system_prompt` ОБЯЗАТЕЛЬНО заполнить — без него API вернёт 404
- `mode_template` с `is_chat_based=false` и `route_suffix=/test/SLUG` — без этого тест не появится на хабе

- После выполнения SQL — **обязательно** пройти тест в браузере до результатов

#### Принципы дизайна

**Зачем тест:** лидмагнит (вовлечение без регистрации) + диагностика (какие темы релевантны) + данные для портрета (текстовые ответы).

**Шкалы из книги, не из головы:**
1. Анализ книги → выделить ключевые паттерны/темы
2. Каждая шкала привязана к конкретным режимам программы
3. 3-12 шкал (оптимально для radar chart)
4. Для каждой шкалы — **ресурс в минусе** (правило 5 тона)

**Вопросы:**
- **4-6 вопросов на шкалу** (оптимум 5: 3 direct + 2 reverse)
- **Не больше 40 вопросов** всего (ЦА с телефона, 10-15 минут)
- Формат: **утверждения** (не вопросы), конкретное поведение за 2-4 недели
- Без двойного отрицания, без сложных конструкций
- Нормализующие формулировки (не давят, не стыдят)
- Гендерно-нейтральные: `мог(ла)`, `ответственным(-ой)`, `выбирал(а)`

**Порядок (КРИТИЧНО) — вопросы группируются по шкалам блоками:**

В `test_configs.questions[]` — все вопросы одной шкалы идут подряд `questions_per_block` штук, потом следующая шкала, и так далее. Между блоками показывается экран «Блок N пройден / Следующий: <название шкалы>».

Если шкалы перемешать (Q1=шкала_A, Q2=шкала_B, Q3=шкала_A...) — между Q4 и Q5 покажется «Блок 1 / Следующий: Нежность», а в Q6 окажется вопрос не из нежности. Пользователь видит несоответствие, теряет доверие к тесту.

Линтер `npm run check:chats` ловит это: проходит по `questions[]` блоками по `ui_config.questions_per_block` и если у вопросов в одном блоке разные `scale` — error.

Прецедент: seven-principles — первая версия чередовала шкалы (Q1=love_map, Q2=fondness, Q3=turn_toward).

**7 правил тона интерпретаций (ОБЯЗАТЕЛЬНО в interpretation_prompt):**
1. НОРМАЛИЗАЦИЯ — через общий опыт, не «у вас проблема»
2. ПОВЕДЕНИЕ, НЕ ЧЕЛОВЕК — «склонны...» вместо «вы такой...»
3. ОСОЗНАНИЕ = ДОСТИЖЕНИЕ — видеть паттерн уже шаг
4. ПРИЧИНА, НЕ ДИАГНОЗ — откуда берётся паттерн
5. РЕСУРС В КАЖДОМ МИНУСЕ — светлая сторона паттерна
6. ЯЗЫК ДВИЖЕНИЯ — «начать», «расти», «развивать»
7. НЕ ПАТОЛОГИЗИРОВАТЬ — запрещены: синдром, нарушение, дисфункция, расстройство. Используй: паттерн, привычка, стратегия, навык

**Формула интерпретации шкалы:** [Ресурс/позитив] + [Обратная сторона через «при этом»] + [Направление роста]. 2-3 предложения.

#### Контент теста (для каждой шкалы)

- **Ключ** (snake_case, с префиксом книги: `ta_`, `ll_`, `ng_`) и **название** (русское)
- **5 вопросов** (3 direct + 2 reverse), утверждения про поведение
- **Ресурс в минусе** — позитивная сторона паттерна (для interpretation_prompt)
- **Связь с режимами** — какой режим раскрывает эту шкалу
- **radar_label** — 1-2 строки для отображения на радар-диаграмме

#### Выход

Готовый SQL seed файл `scripts/seed-{book-slug}-test.sql` по шаблону из PLATFORM_MAP.md. Файл содержит ВСЕ операции: INSERT test_configs + feature flag + test_system_prompt + landing_data + mode_template + program_mode + верификационный SELECT.

### Этап 4.1-retroactive: Ретроспективное добавление теста

Полноценный путь workflow, не эдж-кейс: на платформе уже как минимум две книги прошли через эту модальность (`razgovorny-gipnoz` → `hypnosis-test` в апреле 2026; `100-notes` → `100-notes-test` через несколько дней). Применяется когда у программы уже есть лендинг, портрет, режимы и hub_messages, но теста нет — его решили добавить позже. Этапы 1-3 скилла не повторяются: архетипы и режимы уже в БД.

Выполняй те же 7 SQL-операций из PLATFORM_MAP.md, но с поправками ниже и pre-seed чеклистом в конце раздела.

#### Развилка по доступности исходника

**Есть полный текст книги** (razgovorny-gipnoz кейс) → читай книгу Explore-агентом, сверяй авторскую терминологию со своими seed-промптами режимов. Главный риск — поправка №1 ниже.

**Нет полного текста** (100-notes кейс) → обязателен Deep Research workflow по REFERENCE.md §12 «Книги без полного текста». Требование ≥20 HIGH-цитат, ≥3 на кластер. Промпт с блоком **КРИТИЧЕСКАЯ ДИСАМБИГУАЦИЯ** (REFERENCE.md §12 «Правила атрибуции»). Образцы — `docs/books/100-notes-deep-research-prompt.md` и `docs/books/100-notes-deep-research-prompt-environment.md`.

#### Поправки к 7 SQL-операциям

**1. Не доверяй своим `system_prompt` режимов как источнику терминологии книги.**
Прецедент: для «Разговорного гипноза» Бакирова system_prompts режимов содержали обобщения «общего НЛП» («три фоновые линии», «предикаты V/A/K», «якорение» как наведение транса), которых в книге нет. Тест, спроектированный по промптам, давал бы шкалы не из книги. **Правило:** при ретроспективном добавлении теста перечитай саму книгу (или ключевые главы) и сверь шкалы с авторской структурой материала. Для книг без полного текста — той же цели служит Deep Research с дисамбигуацией автора (см. REFERENCE.md §12).

**2. Шкалы могут не совпадать 1-в-1 с ключами существующих режимов.**
Допустимо: одна шкала привязывается к одному режиму через `program_themes.test_scale_key` + welcome-сценарий темы. Имена ключей шкал (`hypno_rapport_skill`) могут отличаться от ключей режимов (`hypno_rapport`) — главное чтобы тема правильно адресовала пользователя в нужный режим.

**3. Решение «диагностический vs навыковый» — критично.**
- Диагностический (`lower_is_better`): высокий балл = выраженность паттерна, ISSP/GPP. Подходит книгам про патологии/паттерны.
- Навыковый (`higher_is_better`): высокий балл = владение навыком, уровни Новичок→Мастер. Подходит книгам про практику без диагностики (Бакиров — навыки коммуникации; 100-notes — навыки развития).

Критерии — REFERENCE.md секция 12.

**4. RadarChart должен поддерживать `score_direction`.**
До 3-го теста (Бакиров) `RadarChart` хардкодил цвета под `lower_is_better` — для навыкового формата высокие баллы получали красный «тревожный» цвет. После фикса (commit `fix: make RadarChart color logic data-driven`) компонент инвертирует цвета и зоны лейблов на основе `scoring.score_direction`. **Проверь, что эта поддержка есть, прежде чем сидить навыковый тест.**

**5. Регрессия других тестов.**
После любого code-fix в `RadarChart`/`TestResultsPage` — открой результаты ISSP, GPP и hypnosis-test (три существующих теста), убедись что они выглядят как раньше. Регрессия чужих тестов часто маскируется до прода.

| `returning_notest` | Возврат на хаб без прохождения теста | Напоминание про тест + предложение выбрать инструмент |

```sql
UPDATE programs SET hub_messages = jsonb_build_object(
  'first',            '[приветственное сообщение для первого визита, хук про книгу, предложение теста]',
  'returning_test',   'По твоему профилю самые сильные темы — <strong>{theme1}</strong> и <strong>{theme2}</strong>. С чего начнём?',
  'returning_notest', '[напоминание про тест + предложение выбрать инструмент]'
) WHERE slug = 'BOOK_SLUG';
```

Поддерживается ограниченный HTML: `<strong>` для акцента. Плейсхолдеры `{theme1}/{theme2}` в `returning_test` резолвятся в топ-2 тем по баллам теста (см. `app/program/[slug]/(app)/hub/page.tsx`); если у программы нет `program_themes` — стрипаются и выводится `returning_notest`.

**Проверка:** линтер `npm run check:chats` ловит отсутствие любого из 3 ключей (правило `hub-messages-missing` / `hub-messages-key-missing`). Дополнительно — открыть `/program/<slug>/hub?hub_state=first` в браузере и убедиться что Система выводит ожидаемое.

⏸ СТОП не нужен — ленд создаётся на основе утверждённых этапов 1-4.

## Этап 6: Деплой и аудит (обязательно)

Книга не считается выпущенной, пока не задеплоена на боевой сайт и не запущен внешний аудит. Линтер зелёный — это только локальная гарантия SQL/seed-формата. Боевая регрессия (кеш, прод-роутинг, реальная БД) ловится только на `nice-guy-ai.vercel.app`.

### 6.1 Зафиксируй переменные книги

Перед деплоем явно зафиксируй в чате (это критично для подстановки в промпт новой задачи ниже):

- `BOOK_SLUG` — slug программы в БД (напр. `seven-principles`, `games-people-play`). Дефисы, не подчёркивания.
- `BOOK_SLUG_SNAKE` — то же название в snake_case (напр. `seven_principles`, `games_people_play`) — используется в именах выходных файлов.
- `BOOK_TITLE` — русское название книги (для отчёта).
- `LANDING_URL` = `https://nice-guy-ai.vercel.app/program/<BOOK_SLUG>` — публичный лендинг.

### 6.2 Применить миграции

Если есть незаприменённые миграции из этапов 4 / 4.1 / 4.5 — применить через `mcp__supabase__apply_migration`. Если уже применены — пропустить. После применения повторно прогнать `npm run check:chats -- --book=<BOOK_SLUG>` — должен быть `0 errors`.

### 6.3 Закоммитить и слить в main

Workflow «по умолчанию завершать задачу деплоем»:

1. `git add` — только релевантные файлы: `scripts/seed-<BOOK_SLUG>.sql`, `<BOOK_SLUG_SNAKE>_MODE_DETAILS.md`, `<BOOK_SLUG_SNAKE>_SYSTEM_PROMPTS.md`, `.claude/skills/book-to-modes/examples/<BOOK_SLUG_SNAKE>.md`, фото автора `public/authors/<BOOK_SLUG>.jpg`, любые правки иконок. НЕ `git add -A`.
2. `git commit` — conventional commit: `feat(<BOOK_SLUG>): добавить программу + режимы (+ тест / + портрет)`. Co-Authored-By: Claude.
3. `git push -u origin <branch>`.
4. Если работа из worktree-ветки: `gh pr create` → `gh pr merge --squash --delete-branch`. Если прямо в main — `git push origin main`.

### 6.4 Дождаться готовности боевого деплоя

Vercel auto-deploy ~2-3 минуты после merge. Проверка через `WebFetch` боевого `LANDING_URL`:

- Должна вернуться 200, в HTML встречается `BOOK_TITLE`.
- 404 или старый лендинг — подождать ещё минуту, повторить. Максимум 5 минут.
- Если через 5 минут не доехал — проверить `gh run list --limit 3` и Vercel-логи через MCP-инструменты, починить.

### 6.5 Спавн задачи аудита

После того как `LANDING_URL` ответил 200 — вызвать `mcp__ccd_session__spawn_task`:

- **title** (≤60 симв.): `Аудит книги <BOOK_SLUG> после деплоя`
- **tldr**: `Запускает чеклист book-audit по только что задеплоенной книге «<BOOK_TITLE>» и проверяет боевой лендинг. Отдельная сессия — не пачкает контекст создания.`
- **prompt**: см. шаблон в §6.6 ниже.

В UI заказчика появится chip-кнопка. Дальше — его одобрение одним кликом. НЕ пытаться запустить задачу программно и НЕ «эмулировать» аудит в текущей сессии.

### 6.7 Финальный отчёт заказчику — ровно три строки

После того как `spawn_task` отработал и chip в UI:

1. Что закоммитил — одной фразой (напр. «Книга <BOOK_TITLE>: программа, 7 режимов, тест на 5 шкал»).
2. Суть изменения — что увидит на сайте (напр. «На боевом появилась новая программа с лендингом, чатом и тестом»).
3. Ссылка — `<LANDING_URL>`.

Никаких списков файлов, никакого описания chip-задачи — она уже видна в UI как карточка.
