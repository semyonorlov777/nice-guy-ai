# Book-to-Modes: Проектирование режимов Книжный Спарринг по книге

## Обзор

Этот скилл превращает книгу по психологии/саморазвитию в набор из 6-8 режимов Книжный Спарринг с готовыми системными промптами для Gemini API.

**Вход:** Название книги (+ опционально PDF/текст книги). Если у автора несколько связанных книг — можно объединить.
**Выход:** MD-файл с детализацией режимов + MD-файл с готовыми промптами + landing_data JSON + таблица технического маппинга

## 🔴 Перед началом (блокирующий шаг)

**Порядок обязательный — без runbook читать остальное бесполезно, потому что все правила формата кросс-ссылаются туда:**

0. **Прочитай `docs/runbooks/chat-message-formatting.md` целиком.** Это **source of truth** для формата welcome-полей, quick-replies, system_prompt. Скилл лишь оркестрирует пайплайн; правила живут в runbook. Без этого шага гарантированы рецидивы (после прошлых 6 книг каждый раз приходилось делать ~6 fix-*.sql на эти же правила).
1. Прочитай `references/REFERENCE.md` — 53 принципа, 5 архетипов, промпт-шаблон, типология replies, антипаттерны, принципы лендинга (Л1-Л7).
2. Прочитай `references/PLATFORM_MAP.md` — как режимы ложатся на код платформы (таблицы БД, chat_type, SQL, landing_data JSON-схема, **линтер `npm run check:chats`**).
3. Просмотри `examples/` — конспекты решений по прошлым книгам (что сработало, что нет).
4. Если пользователь приложил PDF/текст книги — прочитай его.
5. Если книга не приложена — используй свои знания. Для малоизвестных книг предупреди, что нужен текст.

## Чеклист: объединение книг

Перед началом работы проверь — нужно ли объединять несколько книг в одну программу.

**Когда объединять:**
- У автора 2+ книги, которые дополняют друг друга (теория + практика, диагностика + лечение)
- Одна книга без другой «неполна» — читатель застревает на полпути
- Книги образуют естественную прогрессию

**Примеры:**
- Берн: «Игры» (1964) + «Люди, которые играют в игры» (1972) → объединены в одну программу
- Готтман: «7 принципов» + «The Relationship Cure» → можно объединить
- Одиночная книга → не объединять

**Как объединять:**
1. Определи части программы как прогрессию: «Увидеть → Понять → Действовать» (или другую)
2. Распредели режимы по частям
3. Маппинг: какая книга даёт материал для какой части
4. В таблице режимов добавь колонку «Часть программы»

**Когда НЕ объединять:**
- Книги на одну тему, но разных авторов (Гловер + Берн — это разные программы)
- Книга самодостаточна (Гловер «Славные парни» — одна книга = одна программа)

## Процесс (5 этапов с паузами)

**Ретроспективная модальность.** Если книга уже существует на платформе (есть программа, лендинг и режимы), но теста нет и задача — добавить тест — это отдельный путь: сразу переходи к **Этапу 4.1-retroactive «Ретроспективное добавление теста»** (ниже). Этапы 1-3 пропускаются: архетипы, режимы и промпты уже зафиксированы в БД. Прецеденты: `razgovorny-gipnoz` → `hypnosis-test`, `100-notes` → `100-notes-test`.

### Этап 1: Анализ книги

Изложи:

**Ключевые концепции** — 3-5 главных идей книги. Не пересказ, а «что читатель должен усвоить».

**Навыки/трансформации** — что книга обещает. Формулируй как навык: «распознать X → перестроить Y → получить Z».

**ЦА** — пол, возраст, контекст, уровень боли (низкий = «хочу лучше», средний = «есть проблема», высокий = «кризис»).

**Боли** — 4-6 штук от первого лица: «Я стараюсь, а он/она...», «Не могу понять почему...». Это будущие welcome replies.

**Если объединяешь книги** — укажи какие концепции из какой книги, и как они складываются в прогрессию.

### Этап 2: Маппинг на архетипы

Определи **тип книги** и примени паттерн размножения (см. REFERENCE.md секция 1).

Формула: 5 базовых архетипов + 1-2 подвида самого релевантного = **6-8 режимов** + обязательный **Свободный чат**.

Предложи таблицу:

| # | Название | Архетип | Блум | Часть программы | Суть (1 предложение) |
|---|----------|---------|------|-----------------|----------------------|

Колонка «Часть программы» — обязательна для объединённых книг, опциональна для одиночных.

Объясни: почему именно так, что НЕ включил и почему.

**Checkpoint: нужен ли тест?**

Заполни таблицу критериев (REFERENCE.md §12, нужно ≥3 из 5):

| # | Критерий | Для твоей книги | ✅/⚠️/❌ |
|---|----------|-----------------|---------|
| 1 | Диагностическая/навыковая модель ≥3 шкал | ... | |
| 2 | Шкалы ортогональны (измеряют разное) | ... | |
| 3 | Результат персонализирует дальнейший путь | ... | |
| 4 | Ликерт-утверждения применимы (не эссе) | ... | |
| 5 | Тест работает как воронка (shareable) | ... | |

Отдельно — **достоверность источников** (REFERENCE.md §12 «Книги без полного текста»):
- Полный текст книги есть? / Только фрагменты (рецензии, лекции, соцсети)?
- Если фрагменты — есть ≥20 HIGH-уверенных авторских цитат? Распределены ли они по ≥3 на кластер?
- Если <20 или какой-то кластер <3 → отмечай как ⚠️ и планируй Deep Research ДО SQL-дизайна (см. §12 «Правила атрибуции»).

**Явный вывод:** GO / NO-GO с обоснованием.
- Если GO — укажи: «Тест: да, ~N вопросов, K шкал» + названия шкал и их связь с режимами
- Если NO-GO — укажи «Тест: нет» и почему (какого критерия не хватает, или недостаточно авторского материала; предложи альтернативы из §12)

Покажи checkpoint пользователю. Только после подтверждения переходи к дизайну шкал.

**⏸ СТОП. Дождись подтверждения пользователя.**

### Этап 3: Детализация каждого режима

Для КАЖДОГО режима:

**a) Формат:**
- Архетип (из 5)
- Персона AI: тон, характер, обращение. Определяй по ЦА книги (см. таблицу per-book параметров в REFERENCE.md)
- Какие концепции из книги покрывает

**b) Welcome-сообщение.**

⚠️ Welcome — это **не один текст, а 5 раздельных полей БД** (`program_modes.*`). Каждое имеет свои правила (детали в [chat-message-formatting runbook](../../../docs/runbooks/chat-message-formatting.md) §"Правила по полям"):

| Поле БД | Что туда | Правила |
|---|---|---|
| `welcome_mode_label` | Одно слово-архетип | UPPERCASE: `АНАЛИЗ`, `ВОРКШОП`, `ЛЕКЦИЯ`, `РОЛЕВАЯ`, `ЭКЗАМЕН`, `СВОБОДНЫЙ ЧАТ` |
| `welcome_title` | **Фраза-действие** (что пользователь делает) | Без эмодзи. **НЕ дублировать `mode_templates.name`** — иначе тройной заголовок на карточке (см. REFERENCE.md §8 «Welcome_title vs mode_templates.name»). ✅ «Что ты знаешь о партнёре» (mode `sp_love_map` с name «Карта любви»). ❌ `welcome_title=name=«Карта любви»`. |
| `welcome_subtitle` | Подзаголовок-обещание | Одна строка ≤80 символов, результат-обещание |
| `welcome_ai_message` | Основной ИИ-текст | **Plain text без markdown** (`**`, `#`, `-` не работают). Абзацы через `\n\n`, буллеты через `•`. Макс ~150 слов. Не дублировать title в начале. |
| `welcome_replies` | Кнопки-подсказки | JSONB **объекты** `[{text, type}]`. Не строки. Последний `type: "exit"`. Каждый text ≤60 символов, без вложенных «ёлочек». |

**Контентный шаблон для `welcome_ai_message`** (рендерится в этом поле — без эмодзи+title в начале):

```
[Хук-результат на 1-2 предложения — продаёт что получит пользователь]

Как это работает: [1-2 предложения про формат]

Что ты получишь:
• [конкретный результат 1]
• [конкретный результат 2]
• [конкретный результат 3]
```

**Контентный шаблон для `welcome_replies` (3-4 reply, последний — exit):**

```json
[
  {"text": "[Конкретный голос пользователя по теме режима]", "type": "normal"},
  {"text": "[Другая ситуация]", "type": "normal"},
  {"text": "[Третья ситуация]", "type": "normal"},
  {"text": "Мне сложно сформулировать", "type": "exit"}
]
```

**⚠️ welcome_ai_message рендерится PLAIN TEXT** (без ReactMarkdown — см. [NewChatScreen.tsx:185](../../../components/chat/NewChatScreen.tsx:185) + [chat-message-formatting runbook](../../../docs/runbooks/chat-message-formatting.md)):

- Между абзацами — ТОЛЬКО `\n\n` (двойной перенос). Без него абзацы склеятся в стену — `.nc-ai-text` имеет `white-space: pre-line`, но одиночный `\n` = одна строка.
- Буллет — символ `•`, не markdown `-`/`*` (они напечатаются буквально).
- Не используй `**bold**`, `#` заголовки, нумерованные списки — все эти символы появятся в тексте как литералы.
- Не начинай с `эмодзи + Название режима` — заголовок уже рендерится отдельной карточкой над сообщением (wc-title).

Прецедент: eq-2-0 welcome у всех 5 режимов первоначально рендерился слипшейся стеной — пока не добавили `white-space: pre-line` (коммит `0075501`). Но даже с фиксом без `\n\n` между абзацами сообщение читается как monolith.

**⚠️ Антипаттерны в тексте reply** (проверь каждый reply перед записью в SQL):

- ❌ **Вложенные «ёлочки» внутри reply:** `«Что значит «развитие»?»` — parseQuickReplies regex non-greedy, захватит только до первого `»` → кнопка будет с обрезанным текстом. Убирай внутренние кавычки или переформулируй.
- ❌ **Пунктуация снаружи «ёлочек»:** `«Текст».` — точка вне кавычек ломает regex `[»]$`. Вся пунктуация — только внутри.
- ❌ **Markdown внутри reply:** `«Это **важно**»` — звёздочки видны буквально в UI.
- ❌ **Reply длиннее ~60 символов** — не влезает в кнопку на мобилке.

**c) Паттерн диалога** — 3-5 фаз:
- Что происходит на каждой фазе
- Примеры вопросов AI
- Suggested replies на каждой фазе (тип из типологии — см. REFERENCE.md)
- Где scaffolding fading (4→2→0 replies)
- Где affect labeling («опиши чувство одним словом»)
- Где retrieval practice («что помнишь из прошлого раза?»)
- Где prior knowledge activation («вспомни ситуацию из жизни, когда...»)

**d) Кросс-режимная связка** (формализованный формат):
```
ПЕРЕДАЁТ → режим_name: variable_name (тип)
ПОЛУЧАЕТ ← режим_name: variable_name (тип)
```

Используй стандартные имена переменных из REFERENCE.md секция 9.

В конце этапа 3 — **сводная таблица кросс-режимных связок** (из → в → данные).

**⏸ СТОП. Дождись подтверждения пользователя.**

### Этап 4: Системные промпты для Gemini API

Для КАЖДОГО режима — готовый промпт. Структура:

```
## РОЛЬ
[Кто ты, тон, обращение]

## КНИГА
[Ключевые концепции для ЭТОГО режима — не вся книга, а релевантный срез]

## ПРАВИЛА ОТВЕТА
[Вставить промпт-шаблон из REFERENCE.md §5 — секция «Промпт-шаблон»]

⚠️ **ПРИ ВСТАВКЕ ОБЯЗАТЕЛЬНО** в блоке `### Quick replies — ФОРМАТ` должны быть **три части**:

1. **ПРАВИЛЬНО** — 3 тематически-конкретные «ёлочки» (плейсхолдеры из шаблона заменены под домен режима, от первого лица пользователя, последний — exit).
   - Gemini трактует literal `«Вариант 1»` как дословный output template и копирует буквально → парсер получает plain-текст без «ёлочек» → кнопок нет.
   - Примеры замен — в REFERENCE.md §5 под блоком шаблона.
   - Прецедент: eq-2-0 (коммиты `7707969` + `455c805`) — все 5 режимов выдавали plain-text «Вариант 1/2/3» пока не поменяли на тематические примеры типа «Это злость, я понял» / «Попробую дыхание в следующий раз».

2. **НЕПРАВИЛЬНО (все на одной строке):** `«Вариант 1» «Вариант 2» «Вариант 3»` — частый баг "склейка через пробел".
   - Регэксп парсера требует каждую ёлочку на отдельной строке.
   - Прецедент: каждая из 6 книг получила `fix-{slug}-strengthen-quick-reply-rule.sql` после первичного seed-а.

3. **НЕПРАВИЛЬНО:** `<текст>` — угловые скобки, парсер их не видит.
   - Gemini временами выдаёт `<вариант>` если в промпте нет явного запрета.
   - Прецедент: коммит `d2067ba` `fix-all-books-angle-bracket-counterexample-2026-04-25.sql` — пришлось патчить **все 6 книг разом**. Не повторяй это для новой.

Все три части — **обязательны в КАЖДОМ** system_prompt: режима, programs.system_prompt, programs.author_chat_system_prompt, programs.anonymous_system_prompt. Линтер `npm run check:chats` поймает отсутствие counterexamples.

## WELCOME
[Welcome-сообщение из этапа 3b]

## ЛОГИКА ДИАЛОГА
[Фазы из этапа 3c: что делать, когда переходить, примеры вопросов]

## SUGGESTED REPLIES
[Конкретные replies для каждой фазы: текст + тип]

## НАУЧНЫЕ ПРИНЦИПЫ
- Process-level feedback (не «молодец», а «ты заметил X — точно, потому что Y»)
- Prior knowledge activation (перед темой: «вспомни ситуацию из жизни»)
- Affect labeling (перед глубокой темой: «опиши чувство одним словом»)
- Scaffolding fading (turns 1-5: 3-4 replies, 6-12: 2, 13+: 0-1)
- Desirable difficulties (при ошибке: наводящий вопрос, не ответ)

## КРОСС-РЕЖИМНАЯ СВЯЗКА
[Что передаёт / получает — формализованный формат]

## АНТИПАТТЕРНЫ (НИКОГДА)
- Стены текста (макс 60-80 слов)
- Похвала личности («молодец», «отлично»)
- Replies = дубликат текста ИИ
- Replies от третьего лица / вопросы ИИ
- Overdiagnosis (презумпция нормы)
- Геймификация (стрики, бейджи)
- Давление («ты пропустил», «давай быстрее»)
- Несколько вопросов за раз
- Предположения о поле/ориентации до уточнения
```

В конце этапа 4 — **таблица технического маппинга** (см. PLATFORM_MAP.md):

| Режим | mode_template.key | chat_type | route_suffix | icon | icon_exists? | sort_order |
|-------|-------------------|-----------|-------------|------|-------------|------------|

Колонка `icon_exists?` — проверь по списку в PLATFORM_MAP.md секция «Иконки режимов». Если ❌ → добавь задачу: создать иконку в **трёх файлах** (mode-icons.tsx, hub-icons.tsx, InstrumentList.tsx) + добавить toolKeyMap для chat-based режимов. Подробности в PLATFORM_MAP.md → «Чеклист при добавлении иконки».

**Если у программы есть Темы** (program_themes) — добавь таблицу маппинга тем → режимы (см. PLATFORM_MAP.md секция «program_themes → режимы»).

Каждый промпт должен быть **готовым для вставки** в Gemini API — не абстрактным, а рабочим. Оборачивай в блоки ``` для копирования.

#### ⚠️ КРИТИЧНО: программные промпты и welcome-поля

После того как ты расписал `program_modes.system_prompt` для каждого режима, **ОБЯЗАТЕЛЬНО** обнови программные поля в таблице `programs` — иначе free_chat, author_chat, anonymous-чат и все темы программы потеряют кнопки в диалоге.

В **каждый** из четырёх типов промптов программы должны попасть **четыре кирпича** из [REFERENCE.md §5.0](references/REFERENCE.md):

| Поле | Кирпич А «ОБРАЩЕНИЕ» | Кирпич Б «ЗАПРЕТ ПРИВЕТСТВИЙ» | Кирпич В «Quick replies» | Кирпич Г «Снижение подсказок» |
|---|---|---|---|---|
| `programs.system_prompt` | ✅ | ✅ | ✅ | ✅ |
| `programs.author_chat_system_prompt` | ⚡ (если автор не оговаривает сам) | ✅ | ✅ | ✅ |
| `programs.anonymous_system_prompt` | ✅ | ✅ | ✅ (укороченный) | необязательно |
| `program_modes.system_prompt` каждого режима | ✅ | ✅ | ✅ | ✅ |

Дополнительно для `anonymous_system_prompt`:
- **Кирпич Д** «СТРУКТУРА ПЕРВОГО ОТВЕТА» с `**ОБЯЗАТЕЛЬНО назови концепт книги по имени**` — без этого AI отвечает общими словами без названия методики. Перечисли концепты явно (5-7 имён из `landing_data.main_concepts`).
- **Кирпич Е** «Quick replies — КРИТИЧЕСКОЕ ПРАВИЛО» с явным требованием «в КАЖДОМ из первых ДВУХ ответов 3-4 ёлочки» **и** контр-примером «без кавычек — это НЕ кнопки».

И стартовые «ёлочки» в welcome-полях:

3. **`programs.free_chat_welcome`** — в конец (через `\n\n`) добавь 3–4 стартовые «ёлочки» от первого лица, последняя — безопасный exit. Без этого при заходе в существующий free-чат через ChatWindow стартовых кнопок не будет (parseQuickReplies ищет «ёлочки» именно тут).

4. **`programs.author_chat_welcome`** — то же самое для author-чата. Убирай вложенные «ёлочки» в тексте кнопок (см. антипаттерны Этап 3b).

```sql
UPDATE programs
SET
  system_prompt = system_prompt || E'\n\n## ФОРМАТ QUICK REPLIES\n\n<полный блок из REFERENCE.md §5>',
```

**Верификация (обязательная):** после INSERT в БД пройди 3 сценария в UI:
- `/program/<slug>/chat` (free) → должны быть стартовые кнопки + AI в ответе даёт «ёлочки».
- Клик на тему на хабе → новый чат → AI в ответе даёт «ёлочки».

### Технические детали runtime (FYI для автора seed)

Что код делает поверх seed — знай, чтобы не дублировать работу и не путаться:

1. **QR-reminder auto-inject.** [app/api/chat/route.ts](../../../app/api/chat/route.ts) добавляет напоминание про «ёлочки» в **КОНЕЦ** system_prompt перед отправкой в Gemini (recency effect — последнее видит модель). Это страховка от мелких сбоев модели. **НЕ повод опускать блок `### Quick replies — ФОРМАТ` в seed:** reminder применяется только в `/api/chat`, не в `/api/chat/anonymous` (где есть свой укороченный) и не в `/api/test` (где идёт `programs.test_system_prompt`). Промпт в seed должен быть самодостаточным.

2. **Welcome serialization for F5.** В seed мы пишем `welcome_ai_message` и `welcome_replies` в **разные поля** БД. Runtime-функция `serializeWelcomeWithReplies` в [lib/chat/prepare-context.ts](../../../lib/chat/prepare-context.ts) склеивает их в один text с «ёлочками» в конце и сохраняет в `messages.content` — чтобы после F5 (или загрузки истории) `parseQuickReplies` восстановил кнопки из сохранённого текста.
   - **НЕ заполняй `welcome_message` (legacy) и `welcome_ai_message` одновременно** — приоритет идёт legacy → новые поля теряются. Линтер `npm run check:chats` это ловит (`welcome-message-exclusive`).

3. **AIBubble + QuickReplyBar split.** Все чат-поверхности (ChatWindow, NewChatScreen, AnonymousChat) рендерят ИИ-сообщения через ДВА компонента из [components/chat/ChatMessage.tsx](../../../components/chat/ChatMessage.tsx). `QuickReplyBar` — SIBLING контейнера `.msg`/`.nc-msg`, **НЕ внутри**. Эта деталь не должна волновать автора seed, но влияет на новые чат-экраны: если делаешь — следуй шаблону из runbook §"Шаблон для нового чат-экрана". Прецедент: первая итерация (2026-04-23) рендерила кнопки внутри flex-row — они уехали в узкую колонку справа.

4. **Иерархия system_prompt при выборе.** `lib/chat/prepare-context.ts::loadProgramContext` (строки 146+) выбирает по приоритету:
   1. `program_modes.system_prompt` (для tool-режимов — переопределяет программный, **правила не наследуются**)
   2. `programs.author_chat_system_prompt` (если `chatType === "author"`)
   3. `programs.system_prompt` (дефолт для free_chat и всех тем — `program_themes.welcome_system_context` подмешивается именно к нему через префикс `КОНТЕКСТ ТЕМЫ:`)

   **Импликация:** блок `### Quick replies — ФОРМАТ` обязан быть в КАЖДОМ из этих 3 полей. Если только в одном — другие пути генерации идут без правил.

#### Принципы дизайна

**Зачем тест:** лидмагнит (вовлечение без регистрации) + диагностика (какие темы релевантны) + данные для портрета (текстовые ответы).

**Шкалы из книги, не из головы:**
1. Анализ книги → выделить ключевые паттерны/темы
2. Каждая шкала привязана к конкретным режимам программы
3. 3-12 шкал (оптимально для radar chart)
4. Для каждой шкалы — **ресурс в минусе** (правило 5 тона)

**Вопросы:**
- **4-6 вопросов на шкалу** (оптимум 5: 3 direct + 2 reverse)
- **Не больше 40 вопросов** всего (ЦА с телефона, 10-15 минут)
- Формат: **утверждения** (не вопросы), конкретное поведение за 2-4 недели
- Без двойного отрицания, без сложных конструкций
- Нормализующие формулировки (не давят, не стыдят)
- Гендерно-нейтральные: `мог(ла)`, `ответственным(-ой)`, `выбирал(а)`

**Порядок (КРИТИЧНО) — вопросы группируются по шкалам блоками:**

В `test_configs.questions[]` — все вопросы одной шкалы идут подряд `questions_per_block` штук, потом следующая шкала, и так далее. Между блоками показывается экран «Блок N пройден / Следующий: <название шкалы>».

Если шкалы перемешать (Q1=шкала_A, Q2=шкала_B, Q3=шкала_A...) — между Q4 и Q5 покажется «Блок 1 / Следующий: Нежность», а в Q6 окажется вопрос не из нежности. Пользователь видит несоответствие, теряет доверие к тесту.

Линтер `npm run check:chats` ловит это: проходит по `questions[]` блоками по `ui_config.questions_per_block` и если у вопросов в одном блоке разные `scale` — error.

Прецедент: seven-principles — первая версия чередовала шкалы (Q1=love_map, Q2=fondness, Q3=turn_toward).

**7 правил тона интерпретаций (ОБЯЗАТЕЛЬНО в interpretation_prompt):**
1. НОРМАЛИЗАЦИЯ — через общий опыт, не «у вас проблема»
2. ПОВЕДЕНИЕ, НЕ ЧЕЛОВЕК — «склонны...» вместо «вы такой...»
3. ОСОЗНАНИЕ = ДОСТИЖЕНИЕ — видеть паттерн уже шаг
4. ПРИЧИНА, НЕ ДИАГНОЗ — откуда берётся паттерн
5. РЕСУРС В КАЖДОМ МИНУСЕ — светлая сторона паттерна
6. ЯЗЫК ДВИЖЕНИЯ — «начать», «расти», «развивать»
7. НЕ ПАТОЛОГИЗИРОВАТЬ — запрещены: синдром, нарушение, дисфункция, расстройство. Используй: паттерн, привычка, стратегия, навык

**Формула интерпретации шкалы:** [Ресурс/позитив] + [Обратная сторона через «при этом»] + [Направление роста]. 2-3 предложения.

#### Контент теста (для каждой шкалы)

- **Ключ** (snake_case, с префиксом книги: `ta_`, `ll_`, `ng_`) и **название** (русское)
- **5 вопросов** (3 direct + 2 reverse), утверждения про поведение
- **Ресурс в минусе** — позитивная сторона паттерна (для interpretation_prompt)
- **Связь с режимами** — какой режим раскрывает эту шкалу
- **radar_label** — 1-2 строки для отображения на радар-диаграмме

#### Выход

Готовый SQL seed файл `scripts/seed-{book-slug}-test.sql` по шаблону из PLATFORM_MAP.md. Файл содержит ВСЕ операции: INSERT test_configs + feature flag + test_system_prompt + landing_data + mode_template + program_mode + верификационный SELECT.

### Этап 4.1-retroactive: Ретроспективное добавление теста

Полноценный путь workflow, не эдж-кейс: на платформе уже как минимум две книги прошли через эту модальность (`razgovorny-gipnoz` → `hypnosis-test` в апреле 2026; `100-notes` → `100-notes-test` через несколько дней). Применяется когда у программы уже есть лендинг, портрет, режимы и hub_messages, но теста нет — его решили добавить позже. Этапы 1-3 скилла не повторяются: архетипы и режимы уже в БД.

Выполняй те же 7 SQL-операций из PLATFORM_MAP.md, но с поправками ниже и pre-seed чеклистом в конце раздела.

#### Развилка по доступности исходника

**Есть полный текст книги** (razgovorny-gipnoz кейс) → читай книгу Explore-агентом, сверяй авторскую терминологию со своими seed-промптами режимов. Главный риск — поправка №1 ниже.

**Нет полного текста** (100-notes кейс) → обязателен Deep Research workflow по REFERENCE.md §12 «Книги без полного текста». Требование ≥20 HIGH-цитат, ≥3 на кластер. Промпт с блоком **КРИТИЧЕСКАЯ ДИСАМБИГУАЦИЯ** (REFERENCE.md §12 «Правила атрибуции»). Образцы — `docs/books/100-notes-deep-research-prompt.md` и `docs/books/100-notes-deep-research-prompt-environment.md`.

#### Поправки к 7 SQL-операциям

**1. Не доверяй своим `system_prompt` режимов как источнику терминологии книги.**
Прецедент: для «Разговорного гипноза» Бакирова system_prompts режимов содержали обобщения «общего НЛП» («три фоновые линии», «предикаты V/A/K», «якорение» как наведение транса), которых в книге нет. Тест, спроектированный по промптам, давал бы шкалы не из книги. **Правило:** при ретроспективном добавлении теста перечитай саму книгу (или ключевые главы) и сверь шкалы с авторской структурой материала. Для книг без полного текста — той же цели служит Deep Research с дисамбигуацией автора (см. REFERENCE.md §12).

**2. Шкалы могут не совпадать 1-в-1 с ключами существующих режимов.**
Допустимо: одна шкала привязывается к одному режиму через `program_themes.test_scale_key` + welcome-сценарий темы. Имена ключей шкал (`hypno_rapport_skill`) могут отличаться от ключей режимов (`hypno_rapport`) — главное чтобы тема правильно адресовала пользователя в нужный режим.

**3. Решение «диагностический vs навыковый» — критично.**
- Диагностический (`lower_is_better`): высокий балл = выраженность паттерна, ISSP/GPP. Подходит книгам про патологии/паттерны.
- Навыковый (`higher_is_better`): высокий балл = владение навыком, уровни Новичок→Мастер. Подходит книгам про практику без диагностики (Бакиров — навыки коммуникации; 100-notes — навыки развития).

Критерии — REFERENCE.md секция 12.

**4. RadarChart должен поддерживать `score_direction`.**
До 3-го теста (Бакиров) `RadarChart` хардкодил цвета под `lower_is_better` — для навыкового формата высокие баллы получали красный «тревожный» цвет. После фикса (commit `fix: make RadarChart color logic data-driven`) компонент инвертирует цвета и зоны лейблов на основе `scoring.score_direction`. **Проверь, что эта поддержка есть, прежде чем сидить навыковый тест.**

**5. Регрессия других тестов.**
После любого code-fix в `RadarChart`/`TestResultsPage` — открой результаты ISSP, GPP и hypnosis-test (три существующих теста), убедись что они выглядят как раньше. Регрессия чужих тестов часто маскируется до прода.

### Этап 4.8: Линтер + UI-верификация (ОБЯЗАТЕЛЬНО — до объявления книги готовой)

После выполнения всех SQL — **до** ретроспективы Этапа 5 и **до** объявления книги готовой — прогоняем верификацию. Цель: не оставлять ничего, что вылезет потом в виде `fix-*.sql`.

#### 1) 🔴 Автоматический линтер (обязательный шаг)

```bash
npm run check:chats -- --book=<slug>   # только новая книга — быстрее
npm run check:chats                    # все книги
```

**🔴 Без 0 errors на новой книге считаем что книга НЕ готова.** Если линтер ругается — починить промпты/SQL/seed-файл, перевыполнить INSERT/UPDATE в БД, **снова** прогнать линтер. Не объявлять «книга готова» до зелёного линтера.

Линтер ([scripts/check-chat-seed.ts](../../../scripts/check-chat-seed.ts)) автоматически ловит все типовые fix-паттерны и регрессии из аудитов прошлых книг:

**Welcome-поля карточки режима:**
- markdown в `welcome_ai_message` (`**bold**`, `## headings`, dash-списки)
- эмодзи+`**Title**` в начале `welcome_ai_message` (дубликат `welcome_title`)
- `welcome_replies` как строки вместо объектов `{text, type}`
- `welcome_mode_label` не UPPERCASE
- `welcome_title` начинается с эмодзи
- **`welcome_title` дублирует `mode_templates.name`** (фраза действия обязательна — урок Готтмана)
- `welcome_subtitle` > 80 символов

**system_prompt (на всех уровнях):**
- без блока Quick replies / без counterexample про склейку / без counterexample про `<угловые скобки>`
- **без блока «Запрет приветствий»** (кирпич Б REFERENCE.md §5.0)
- **без блока «ОБРАЩЕНИЕ» с правилом «ты»** (кирпич А)
- `programs.system_prompt` / `author_chat_system_prompt` / `anonymous_system_prompt` без QR-блока (правила не наследуются между уровнями)
- `programs.free_chat_welcome` / `author_chat_welcome` без `«ёлочек»` в конце (стартовых кнопок не будет)
- `program_themes.welcome_system_context` дублирует QR-блок (он наследуется из `programs.system_prompt`)

**anonymous_system_prompt — дополнительные обязательные блоки:**
- **«СТРУКТУРА ПЕРВОГО ОТВЕТА» с `ОБЯЗАТЕЛЬНО назови ... по имени`** (блок Д) — иначе AI отвечает общими словами без названия концепта
- **«Quick replies — КРИТИЧЕСКОЕ ПРАВИЛО» с контр-примером «без кавычек»** (блок Е) — иначе AI выводит варианты простым текстом без кликабельных кнопок

**Landing и тест:**
- `landing_data.author.photo_url` не локальный путь
- `landing_data.main_concepts` отсутствует или пустой/<5 элементов
- HTML-теги (`<em>`, `<strong>`, `<br>`) в полях лендинга без поддержки разметки (`landing_data.chat_header.*`, `book.*`, `personas.items[].body`)
- В `test_configs.questions[]` шкалы перемешаны внутри блока `ui_config.questions_per_block`

**Прочее:**
- `welcome_message` (legacy) и `welcome_ai_message` заполнены одновременно — приоритет legacy → новые поля теряются

**Если линтер вернул ошибки** — фиксать в seed, перевыполнять INSERT/UPDATE, не накручивать новые fix-*.sql после.
