# ADR: Интеграция анкеты с системой cross-mode связей платформы

- **Статус**: Proposed
- **Дата**: 2026-05-20
- **Контекст**: пилот анкеты на nice-guy, перед раскаткой на 12 других книг
- **Авторы**: аудит проведён Claude, утверждается заказчиком

## Контекст

С пилот-релизом анкеты (PR #114–#135) платформа получила user-level «факт-карту» в таблице `user_profile_responses`. UI анкеты (`/program/[slug]/anketa`) собирает **3 ответа**: `context_intent` (4 чипа + textarea), `problem` (open-text), `need_payoff` (open-text). Сервис ([lib/personalization.ts](lib/personalization.ts)) умеет читать 4 поля (`IDENTITY_QUESTION_IDS` = тех 3 + `implication`) — четвёртый зарезервирован под soft-onboarding-извлечение из чата, но логики записи AI-ответа обратно в БД пока нет.

Текст анкеты префиксируется к системному промпту через `buildPersonalizationContext()` → блоки `## КТО ПЕРЕД ТОБОЙ` и `## SOFT-ONBOARDING`.

Платформа параллельно содержит **развитую систему связей** между тренажёрами:
- портрет (`portraits.content.ai_context`), обновляемый Gemini Pro каждые 5 user-сообщений
- тест ISSP (7 шкал) → `appendTestScores()` в промпт
- темы хаба, упорядоченные по результатам теста ([lib/queries/themes.ts:51-62](lib/queries/themes.ts))
- hub_welcome с плейсхолдерами `{theme1}/{theme2}` ([app/program/[slug]/(app)/hub/page.tsx:129-142](app/program/[slug]/(app)/hub/page.tsx))
- calibration (для книг с режимом `pishi_calibration`)
- (легаси) плейсхолдер `{{cross_mode_data}}` — упоминается в промптах других книг, в коде runtime не подменяется; в nice-guy не используется

Анкета сейчас не участвует ни в одной из этих связей, кроме инжекции в начало промпта. Вопрос: где это безвредно, а где она должна встроиться **до** копирования на остальные книги.

## Карта существующих связей в Гловере

### Жизненный цикл системного промпта ([app/api/chat/route.ts:59-80](app/api/chat/route.ts))

```
[1. КТО ПЕРЕД ТОБОЙ + SOFT-ONBOARDING]  ← анкета, префикс
---
[2. base mode/program system_prompt]    ← из БД (program_modes / programs)
---
[3. КОНТЕКСТ ПОЛЬЗОВАТЕЛЯ из портрета]  ← appendPortraitContext (ai_context, 200-300 слов)
[4. РЕЗУЛЬТАТЫ ТЕСТА]                   ← appendTestScores (JSON ISSP-баллов)
[5. КАЛИБРОВКА]                         ← appendCalibrationContext (для nice-guy = пусто)
[6. КОНТЕКСТ ТЕМЫ]                      ← topicContext из body
---
[7. QR-reminder]                        ← про формат ёлочек, последний для recency
```

`buildPersonalizationContext`, `appendTestScores`, `appendCalibrationContext` гоняются параллельно через `Promise.all` (route.ts:65-69).

### Источники cross-mode персонализации

| Источник | Откуда собирается | Куда инжектится | Условие |
|---|---|---|---|
| **Test scores** | `test_results` (ISSP, 7 шкал) | system_prompt suffix | `status='ready'` |
| **Portrait.ai_context** | Gemini Pro анализирует историю чатов упражнений | system_prompt suffix | каждые 5 user-сообщений в exercise-чате |
| **Темы хаба** | 7 тем привязаны к шкалам ISSP через `test_scale_key` | hub UI + `{theme1}/{theme2}` в welcome | если тест пройден — sort by score; иначе sort_order |
| **`{{cross_mode_data}}`** | — | — | В Гловере не используется (легаси из других книг) |
| **Анкета** | `user_profile_responses` | system_prompt prefix | для всех чатов кроме test-like (`test`, `exam`, `archetype-test`) |

### Темы Гловера (7 шт)

Перестать угождать · Не обижаться молча · Вернуть свои потребности · Отпустить контроль · Говорить «нет» · Найти мужскую опору · Быть собой в отношениях

Привязаны к ISSP-шкалам (`test_scale_key`). Порядок:
- тест пройден → `score DESC` (горячие сверху)
- тест не пройден → `sort_order` (статика)
- **анкеты в этой логике нет** — `getThemesOrdered(themes, testScores?)` второй параметр опционален

### Hub welcome (Гловер)

`programs.hub_messages` = `null` для nice-guy. Welcome берётся из `free_chat_welcome` / `author_chat_welcome` — статичные строки. Плейсхолдеры `{theme1}/{theme2}` обрабатываются кодом, но для Гловера в БД не настроены — то есть и эта связь у Гловера сейчас не используется.

### Портрет (Гловер)

`programs.portrait_prompt` — большая инструкция (500+ строк) для Gemini Pro: дополнять, не перезаписывать, intensity (noticed/medium/high), ai_context 200-300 слов. Источник данных портрета — **только** истории чатов упражнений (chat_type=`ng_exercises`). Из других режимов (теория, кейсы) портрет не обновляется.

## Где дыры: точки, где анкета должна влиять, но не влияет

| # | Точка | Текущее поведение | Что теряется |
|---|---|---|---|
| 1 | **Portrait analyzer** | Gemini Pro видит историю чата + текущий портрет, **не видит** identity_facts | Аналитик упускает контекст «почему человек пришёл», `ai_context` не учитывает SPIN-картину |
| 2 | **Темы хаба без теста** | `getThemesOrdered` смотрит только `testScores` | Если тест не пройден, но анкета есть — темы идут по статичному `sort_order`. Теряется «эта программа узнаёт меня» при первом заходе |
| 3 | **Hub welcome** | Для returning-notest — статика (или пусто, для Гловера `hub_messages=null`) | Можно подставить `problem` или адаптировать к `context_intent` |
| 4 | **Welcome режимов** | Статичные строки `welcome_message` | Анкета попадает в КТО ПЕРЕД ТОБОЙ только в первом **ответе** AI после старта — welcome AI пользователь видит **до** ответа AI |
| 5 | **Порядок 46 упражнений** | Sequential (1→46) | Если `problem` про границы — упражнения про границы могли бы сдвинуться вверх |
| 6 | **`source='soft_onboarding'`** | Поле в БД есть, write-back логика не реализована | Когда AI извлекает `implication` в чате, не сохраняет обратно в `user_profile_responses` |
| 7 | **`confirmed_at`** | Поле в БД есть, логика не реализована | На второй книге не переиспользуется ответ из первой |

## Рекомендации для пилота (Гловер)

### P1 — Анкету в portrait analyzer (высокий приоритет, ≈30 строк кода)

В [lib/portrait-updater.ts](lib/portrait-updater.ts) функция `analyzeForPortrait` сейчас передаёт Gemini Pro только историю чата + текущий портрет. Добавить блок identity-фактов в её промпт:

```
ИДЕНТИЧНОСТЬ ПОЛЬЗОВАТЕЛЯ (из анкеты):
- Контекст: {context_intent}
- Проблема: {problem}
- Цель: {need_payoff}
```

(Без `implication` — его в анкете нет; добавлять только если поле появится через soft-onboarding-write-back.)

**Что даёт пользователю:** портрет становится точнее — `ai_context` начинает звучать как «AI помнит проблему пользователя на фоне его изначального запроса», а не «AI наблюдает реплики». Усиливает эффект continuity между сессиями.

**Стоимость:** один `getFacts()` в начале `analyzeForPortrait`, текстовый блок в template.

### P2 — Темы по анкете когда нет теста (средний приоритет, ≈50 строк кода)

Расширить [lib/queries/themes.ts:51](lib/queries/themes.ts) — `getThemesOrdered(themes, testScores)` → `getThemesOrdered(themes, { testScores?, identityFacts? })`.

Логика (если теста нет, но анкета есть):
- ключевые слова в `problem` / `context_intent` → маппинг на `theme.title` или новое поле `theme.anketa_tags[]`
- например: «границы», «сказать нет» → темы «Говорить нет» / «Не обижаться молча» первые
- fallback: `sort_order` если ничего не матчится

**Что даёт пользователю:** первое впечатление хаба = «эта программа понимает, зачем я здесь», даже без диагностики ISSP. Прямо влияет на funnel: хаб → первое сообщение в чате.

**Стоимость:** seed обновляется (или новое поле `anketa_tags`), `hub/page.tsx:121` передаёт facts в `getThemesOrdered`. Маппинг можно сначала захардкодить, потом вынести в БД.

### P3 — Welcome хаба видит анкету (низкий приоритет, ≈20 строк кода)

В [app/program/[slug]/(app)/hub/page.tsx:129-142](app/program/[slug]/(app)/hub/page.tsx) добавить плейсхолдеры:
- `{user_problem}` → `facts.problem`
- `{user_intent}` → метка выбранного `context_intent` (по `value`)

Шаблон Гловера для returning-notest может стать: «Ты говорил, что {user_problem}. Давай начнём с темы {theme1}». Для Гловера потребуется заполнить `hub_messages` (сейчас null).

**Что даёт:** ощущение continuity, низкая цена правки. Чистая косметика — не блокер.

### Что НЕ делать на пилоте

- **Не лезть в `{{cross_mode_data}}`** — в Гловере его нет, это копипаста легаси из `borba-za-vnimanie` / `mind-power` / `heroes-and-outlaws`. В рамках Гловера cross-mode = `test_scores + portrait`, плейсхолдер не нужен.
- **Не делать персональный порядок 46 упражнений** — структура книги важнее персонализации, риск сломать педагогику Гловера.
- **Не реализовывать `source='soft_onboarding'`** (вытаскивание из чата) — это P3 для отдельного цикла, нужен AI-extraction + UX-подтверждения.
- **Не реализовывать `confirmed_at`** cross-book — преждевременно, пока книг с анкетой = 1.
- **Не менять `welcome_message`** отдельных режимов — анкета уже видна AI через КТО ПЕРЕД ТОБОЙ, в первом **ответе** AI её учтёт. Welcome — это шаблон до диалога.

Обязательно блок «Анкета (`user_profile_responses`)» с шаблоном `## КТО ПЕРЕД ТОБОЙ` + `## SOFT-ONBOARDING`.

### Правка 2: `SKILL.md` — новый этап «Этап 3.5: Анкета программы»

Чеклист для каждой новой книги:

## Открытые вопросы (нужно стратегическое решение)

### О1. Приоритет конфликта анкета vs тест

Сценарий: анкета говорит `problem = «не могу сказать нет»`, тест ISSP даёт высокий балл по `approval` (угождение), но низкий по `boundaries`. Какую тему ставить первой?

**Гипотеза:** тест > анкета (тест — диагностический инструмент, анкета — субъективное самоощущение). Но для UX, возможно, лучше показывать то, что **человек сам назвал** — увеличивает ощущение «слышу тебя».

**Альтернатива:** показывать сразу две — одну от теста, одну от анкеты, маркируя источник («ты сам сказал», «тест показал»).

### О2. Анкета для всех 13 книг или избирательно?

Если для всех — нужен унифицированный шаблон (3 SPIN-вопроса). Если избирательно — критерий (например, только книги с портретом? только книги с диалоговыми режимами?).

### О3. Унифицированные вопросы vs персональные под книгу?

Сейчас вопросы захардкожены в [lib/anketa/questions.ts](lib/anketa/questions.ts) без привязки к программе (есть только `nice-guy`). Если для разных книг нужны разные формулировки или дополнительные вопросы — нужна миграция: каталог `program_id → custom_questions[]`. Либо вынести вопросы в БД (`program_anketa_questions`).

### О4. Метрика успеха анкеты

Что измерять для оценки P1/P2/P3:
- completion rate анкеты (% дошедших до конца)
- skip rate каждого вопроса
- time-to-first-message (быстрее ли пишет первое сообщение после анкеты)
- retention хаба (возвращается ли)
- качество AI-ответов в первой сессии (сложнее измерять автоматически)

Гипотеза: P1 (анкета в портрет) даст самый заметный эффект в 5-10 сессии, когда портрет накопил данные. P2 (темы по анкете) даст заметный эффект в первой сессии. P3 (welcome) — мелкий бонус.

### О5. Анкета и cross-book flow

Когда человек проходит вторую книгу — переиспользовать ответы из первой автоматически? Или показывать «вот что мы знаем, подтверди»? Это влияет на UX анкеты второй и далее книги, и определяет назначение поля `confirmed_at`.

## Решение

Решает заказчик после ревью ADR. ADR — не план реализации, а карта решений, которые нужно принять до раскатки анкеты на остальные книги.

## Применение к книге `pishi-sokraschay` (май 2026)

Первая итерация масштабирования — Ильяхов «Пиши, сокращай».

### Что сделано

- `lib/anketa/questions.ts` — добавлен ключ `pishi-sokraschay` в `AnketaProgramSlug` и `ANKETA_QUESTIONS` с 3 вопросами:
  1. `context_intent` (hybrid) — «Что у тебя болит с текстами?» + 4 чипа по уровням пирамиды (цель / тезис / структура / стиль)
  2. `problem` (open_text) — «Какие тексты пишешь и что не получается?»
  3. `need_payoff` (open_text) — «Как ты поймёшь, что программа сработала?»
- `app/program/[slug]/(app)/hub/page.tsx` — auto-redirect на анкету снят с захардкоженного `slug === DEFAULT_PROGRAM_SLUG` и переведён на `isAnketaProgram(slug)`. Теперь работает для всех slug-ов из каталога.
- `programs.hub_messages` для `pishi-sokraschay` — добавлены ключи `anketa_only` и `anketa_and_test` (всего 5 состояний). Тексты в стиле Ильяхова, без HTML-маркетинга.
- Из `program_modes` снята привязка режима `pishi_calibration` (старая чат-калибровка). `mode_templates` запись с `key='pishi_calibration'` сохранена для аудита / отката.

### Чем отличается от Гловера

| Аспект | nice-guy (Гловер) | pishi-sokraschay (Ильяхов) |
|---|---|---|
| Тест ISSP | есть (35 вопросов, 7 шкал) | нет |
| `program_themes` | 7 тем, привязаны к шкалам ISSP | таблица пустая |
| Состояния хаба | все 5 (`first` / `returning-test` / `returning-notest` / `anketa-only` / `anketa-and-test`) | де-факто только 3 (`first` / `returning-notest` / `anketa-only`) — состояния с тестом недостижимы |
| Плейсхолдеры | `{theme1}`/`{theme2}` + `{problem}` | только `{problem}` (тем нет — `{theme1}` стрипается, fallback на `returning_notest`) |
| AI-фильтр тем (Gemini Flash) | работает, выбирает 2-4 темы из 7 | возвращает пустой массив (нет тем) — UI хаба показывает секцию «Инструменты» без секции «Темы» |
| Портрет / `analyzeForPortrait` | обновляется из чатов упражнений | у Ильяхова нет упражнений → портрет (`ai_context`) не обновляется. Но блок «Твой запрос — из анкеты» в `/portrait` появляется одинаково (он рендерится из `getFacts`, а не из `portraits.content`) |
| Чем заменяет анкета | дополняет ISSP-тест | **заменяет** старый чат-режим `pishi_calibration` (фуллскрин > чат: структурированные данные, идемпотентные, доступны всем нижестоящим режимам) |

### Замечания для следующих книг (Белоусов «Борьба за внимание», Марк/Пирсон «Герой и бунтарь»)

1. **Состояние `returning-test` для книг без теста — мёртвый код.** Можно либо не определять ключ вовсе (welcome автоматически упадёт в `returning_notest`), либо оставить как safe fallback. Я оставил, в нём подставляется `{problem}` — если когда-то добавят тест, не сломается.
2. **CTA «Пройти тест» на хабе у книги без теста показывается всё равно.** Это унаследовано от Гловера, в task scope не входило, но стоит отдельно проверить логику `HubScreen` — должна скрываться когда у программы нет связанного теста.
3. **Пустые `program_themes` — нормальный кейс** для marketing-книг. AI-фильтр аккуратно возвращает `[]`, hub/page.tsx fallback'ит на `returning_notest`, плейсхолдеры стрипаются. Не надо «временно» вписывать темы для пилота.

### Связка анкеты и теста — ключевой инвариант

Анкета и тест отвечают на **разные** вопросы:

- Тест — про **диагностику** («какие архетипы у тебя сильнее»). Источник: 24 вопроса × 12 шкал.

Они независимы (можно пройти любой из них первым), но welcome `anketa_and_test` склеивает оба слоя в один контекст: «помню задачу + знаю архетипы → даю предметную работу». Это **главное** состояние хаба после полного цикла.

### Замечания для следующей книги (Белоусов «Борьба за внимание»)

1. **Если у книги нет теста с многомерной диагностикой** — `{top1_archetype}/{top2_archetype}` не нужны, regex fallback'а уже корректно их стрипает. Можно оставить из шаблона на будущее, можно не использовать.
2. **Если есть тест с 2+ шкалами** — `getTopScaleNames` универсален: возьмёт топ-N. Имена шкал берутся из `test_configs.scales[*].name`. Имя плейсхолдера в welcome можно адаптировать к домену книги (например `{top1_technique}` для «Борьбы за внимание»). Тогда нужен ещё один regex group в hub/page.tsx — или универсальная схема (например `{top1}`, `{top2}` без attached-context).
3. **Формулировки welcome от первого лица** — частая проблема. Анкета сохраняет фразы в формате «Я строю личный бренд». Подставляя в welcome через «Помню, ты {context_intent}» получаешь «Помню, ты Я строю…» — грамматически ломается. Правильно: формула «Твой запрос — {context_intent}» / «Помню твой запрос — {problem}». Это работает с любым first-person ответом.
4. **`scores_by_scale` хранится как объект `{max, pct, raw, level}`**, не как число. Если потребуется ранжировать по баллу — используй `getTopScaleNames` (он сам разбирается с обоими форматами) либо учитывай в любых новых утилитах.
5. **Калибровочный режим, если есть** (Белоусов имеет chat-based «контексты» калибровку) — снимается через DELETE из `program_modes`, не из каталога `mode_templates`. Это паттерн Ильяхова, проверенный.

### Замечания для будущих книг

1. **Кейс «книга родилась с анкетой → калибровка тона постфактум»** теперь зафиксирован. Если книга только что добавлена, и анкета была написана не автором тренажёра (или генерирована шаблоном), стоит запланировать отдельный проход после добавления книги: пересмотр чипов (привязка к темам тренажёра в seed), пересмотр welcome (тон автора, прокидывание плейсхолдеров правильно).
2. **Привязка чипов к темам — мощный инструмент.** В первой версии the-choice (от #145) чипы были общими `trauma/forgiveness/stuck/loss` — концепции есть, но без явной связи с темами тренажёра. После правки `past/patterns/victimhood/meaning` каждый чип явно мапится на тему (через `anketa_theme_relevance` фильтрацию) — пользователь видит «эта программа понимает, что я выбрал». Это улучшает state `anketa_only` без любого изменения кода.
3. **Тон автора через слова-якоря.** Для Эгер ключевые слова — «свобода», «выбор», «слышу», «если хочешь», «помогла». Антонимы в тоне — «сработала программа», «пройди тест», «исправь». Welcome автора должен звучать как если бы автор говорил с тобой лично. Эту калибровку лучше делать после того как `mode_templates` и `landing_data` уже заполнены — там виден тон автора.
4. **«Книга помогла» vs «программа сработала».** Микроразница, но в welcome/анкете книга-первоисточник звучит теплее. Платформа — инфраструктура; книга — это то, ради чего человек пришёл. Для книг с сильным авторским голосом (Эгер, Гловер) стоит писать «книга помогла». Для маркетинговых (Ильяхов, Белоусов) — «программа сработала» ок (программа = тренажёр, не книга).
5. **State `anketa_only` для книги С тестом** — самый частый сценарий первого захода после анкеты (тест ещё не пройден). Welcome здесь должен мягко звать в тест, не заставляя. Формула «Если хочешь, пройди тест X (Y минут) — он поможет точнее понять, с чего начать» — работает: даёт выбор, объясняет ценность теста (точнее), даёт оценку времени.
